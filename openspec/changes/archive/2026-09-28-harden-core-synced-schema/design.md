## Context

The 10 core synced tables (`merchants, outlets, registers, staff, categories, assets, products, outlet_products, orders, order_items`) were built correctly for the sync engine — every table carries the mandatory `(scope, sync_updated_at)` index on the API side and `is_synced` on the local side. But those indexes serve the engine's pull/push queries, not the application's read paths. The UI queries (`SELECT * FROM products WHERE merchant_id = ? AND is_active = 1 ORDER BY sort_order`) get no index help and degrade as the catalog grows.

Two other latent gaps exist:
1. **`assets.status` enum drift** — the API drizzle enum is `['pending','compressed','pending_upload','ready','failed']`, but `pending_upload` was removed from the live lifecycle when the assets spec was corrected (change `correct-asset-spec-to-client-owned-architecture`, archived). No code writes this value. The local side is untyped `text("status")`, so the two declarations don't even agree.
2. **Onboarding preferences have no home** — the onboarding wizard collects `business_type` (displayed as "F&B"), `use_tax`, and `tax_percentage`. The R14 onboarding spec (auth/spec.md) currently says these are "stored locally, NOT persisted to API." That was an interim dodge, not a design decision. They belong on `merchants`/`outlets`.

Full design rationale lives in `openspec/DATABASE-DESIGN.md` and `docs/plans/2026-06-20-pos-schema-extension-design.md`. This design covers only the hygiene subset.

## Goals / Non-Goals

**Goals:**
- Add the 6 read-path indexes the UI actually needs, on both schema files (mirrored).
- Fix the `assets.status` enum: remove `pending_upload` from API; add the typed enum to local. No SQL migration (type-level only).
- Add 3 preference columns (`business_type`, `use_tax`, `tax_percentage`) additively.
- Regenerate the baresync contract cleanly.
- Generate the API migration and hand-write the matching local migration, verified column-for-column.

**Non-Goals:**
- No new tables. The 8 feature tables (`ingredients`, `inventory_stocks`, `stocktakes`, `stocktake_lines`, `goods_receipts`, `goods_receipt_lines`, `cash_shifts`, `order_item_modifiers`) are a separate change (`extend-pos-domain-tables`).
- No UI consumption of the new columns. Tax *application* at checkout, business-type *flag gating* in the frontend — those are feature changes, not schema-foundation changes.
- No removal of any existing index, column, or constraint. Additive only.
- No tax line-item columns on `orders`/`order_items`. `use_tax`/`tax_percentage` enable calculation; applying tax to order totals is a checkout-flow change.

## Decisions

### D1: Indexes mirror on both schema files, not just local

The UI runs locally, so the read-path indexes matter most on the local side. But the API also runs catalog/report queries (admin endpoints, server-side report generation), and the generator validates that paired tables have matching column sets. Keeping the index set mirrored avoids future "why is this fast locally but slow on the server" confusion and matches the existing pattern (every table has both `*_scope_sync_idx` AND `*_is_synced_idx`, even though only one is used per side).

Alternative considered: local-only indexes. Rejected — the API does run these queries, and the convention is mirror.

### D2: `assets.status` fix is type-level only, no migration

SQLite stores drizzle text enums as plain `text` columns — the enum values are a TypeScript-side constraint, not a DB-level CHECK. Removing `pending_upload` from the enum declaration changes only the TypeScript type; existing rows (none of which carry `pending_upload`) are unaffected. Adding a typed enum to the local side (currently untyped `text("status").notNull().default("pending")`) brings type parity with the API side.

Verified: `grep -r "pending_upload" apps/` returns no writers. The value is dead.

### D3: Preference columns use `fnb` not `f&b` as enum value

Onboarding displays "F&B" but stores `fnb`. The `&` character is URL-unfriendly (query-string encoding) and JSON-unfriendly (string escaping). The enum values are `fnb`, `retail`, `hybrid`.

### D4: `tax_percentage` is integer, not real

Tax rates are conventionally whole percentages (0–100). Indonesia's PPN is 11%. Integer eliminates float drift. If fractional rates ever become necessary (8.25% in some jurisdictions), the migration to `REAL` is additive and low-risk — YAGNI until then.

### D5: Local migration hand-written, matching API migration

The API migration is generated by `drizzle-kit generate` (reliable). The local migration is hand-written SQL in `apps/pos-app/src-tauri/migrations/0001_*.sql` because the Tauri side uses raw SQL files, not drizzle-kit. The two must match column-for-column (modulo sync metadata: local has `is_synced`, API has `sync_updated_at` — both come from the spread, not hand-written).

Highest-risk step is divergence between the two. Mitigation: column-for-column diff in verification gate #5.

### D6: Keep additive columns on the "frozen" tables

"Freeze the 10 core synced tables" (from the brainstorm) means no drops, renames, or type changes — not no additions. Additive columns with defaults are safe: existing rows backfill with the default, sync continues working, no breaking change. This interpretation lets us persist onboarding preferences now without waiting for a table-restructuring change that isn't coming.

## Risks / Trade-offs

- **[Local migration diverges from API migration]** → Mitigation: column-for-column diff in verification. The structural shape is simple here (6 `CREATE INDEX` + 3 `ALTER TABLE ADD COLUMN`), so divergence surface is small.
- **[Indexes add write overhead]** → Every new index slows writes slightly. For POS-scale catalogs (hundreds, not millions, of products) and the existing soft-delete/write-transaction pattern, this is negligible. The read-speed win dominates.
- **[Onboarding R14 spec says preferences are local-only]** → This change contradicts that. Mitigation: update the R14 spec (in this change's delta) to reflect persistence. The local-only wording was interim, not intentional.
- **[No app code consumes the new columns yet]** → Accepted. Schema foundation lands ahead of feature wiring, same pattern as `use-drizzle-query.ts` and the asset pipeline earlier this session.
- **[`assets.status` enum narrowing could break a stale row]** → Verified no row carries `pending_upload`. Even if one did, SQLite doesn't enforce the enum at the DB level — only TypeScript would complain, and the query result would coerce. No data loss risk.

## Migration Plan

**Execution order:**
1. Edit `api-synced-schema.ts`: add 3 columns, fix `assets.status` enum, add 6 read-path indexes.
2. Edit `local-synced-schema.ts`: mirror exactly (same columns, same indexes, typed `assets.status` enum).
3. Run `bun run generate:sync` — verify clean (no `SYNC_SCHEMA_JSON_ONLY_FIELD`, no missing-scope errors, no pairing drift).
4. Run `drizzle-kit generate` in `apps/api` → produces `0002_*.sql`.
5. Hand-write `apps/pos-app/src-tauri/migrations/0001_*.sql` mirroring the structural changes.
6. Verify: API tests (58 baseline), POS-app `tsc` + ultracite + vitest (76 baseline), column-for-column migration diff.

**Rollback:** All changes are additive. Rollback = revert the commit; existing rows already carry the new columns with defaults and continue to work (SQLite ignores extra columns on downgrade within the same major version). The generated contract version advances, but the plugin loads the contract bundled at compile time, so a rollback just reverts the bundle too.

## ADDED Requirements

### Requirement: Server sync repository uses baresync factory
The `apps/api/src/sync/service.ts` file SHALL be replaced with a `createDrizzleSyncRepository` call from `baresync/server/drizzle`, providing one entry per synced table with `buildRow`, `readLatestRow`, `readRows`, `softDeleteRow`, and `upsertRow` functions.

#### Scenario: Repository is created with all 10 tables
- **WHEN** the server starts
- **THEN** the sync repository has entries for all 10 synced tables (merchants, outlets, registers, staff, categories, assets, products, outletProducts, orders, orderItems)

#### Scenario: Each table has 5 functions
- **WHEN** a table entry is accessed
- **THEN** it has `buildRow`, `readLatestRow`, `readRows`, `softDeleteRow`, and `upsertRow` functions

### Requirement: Server routes use baresync factory handlers
The `apps/api/src/sync/routes.ts` file SHALL use `createSyncPushHandler`, `createSyncPullHandler`, and `createSyncStatusHandler` from `baresync/server`.

#### Scenario: Push endpoint handles JSON-encoded payloads
- **WHEN** client sends a push request with JSON-encoded changes
- **THEN** server decodes, validates, and processes the changes

#### Scenario: Pull endpoint returns JSON-encoded changes
- **WHEN** client requests pull with a cursor
- **THEN** server returns JSON-encoded changes with correct scope filtering

#### Scenario: Status endpoint reports changes
- **WHEN** client sends status request with a cursor
- **THEN** server returns whether changes exist since that cursor

#### Scenario: URL paths are preserved
- **WHEN** client calls `/api/sync/push`, `/api/sync/pull`, `/api/sync/status`
- **THEN** endpoints respond correctly (no URL changes)

### Requirement: Push adapters are generated by baresync
The `apps/api/src/sync/push-adapters.generated.ts` file SHALL be deleted. Baresync generates push adapters internally based on the sync contract.

#### Scenario: No manual push adapters
- **WHEN** the server processes a push request
- **THEN** baresync handles table ordering and change application internally

### Requirement: Scope resolution handles dual scope types
The `resolveScope` function SHALL return `{ scopeId, merchantId }` to handle both merchant-scoped and outlet-scoped tables.

#### Scenario: Merchant-scoped request resolves correctly
- **WHEN** a request includes `scopeId: "merchant-123"`
- **THEN** `resolveScope` returns `{ scopeId: "merchant-123", merchantId: "merchant-123" }`

#### Scenario: Outlet-scoped request resolves correctly
- **WHEN** a request includes `scopeId: "outlet-456"`
- **THEN** `resolveScope` returns `{ scopeId: "outlet-456", merchantId: "merchant-123" }` (merchant derived from outlet)

#### Scenario: Invalid scope returns 403
- **WHEN** a request includes an invalid scope ID
- **THEN** `resolveScope` returns `{ ok: false, status: 403, body: { error: "forbidden" } }`

### Requirement: Server sync test coverage
The server sync tests SHALL verify push, pull, and status endpoints with JSON encoding.

#### Scenario: Push test with JSON payload
- **WHEN** test sends a push request with JSON-encoded changes
- **THEN** server processes and returns success

#### Scenario: Pull test with cursor
- **WHEN** test sends a pull request with a cursor
- **THEN** server returns correct changes for the scope

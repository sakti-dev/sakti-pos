# Persisted Product Photo Jobs Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Save product forms immediately while product photo compression, asset linking, cleanup, upload, and crash recovery run through persisted local jobs.

**Architecture:** Product create/update stays on the frontend and no longer waits for WebP compression. When a staged native photo exists, the frontend saves the product first, persists/enqueues a Rust-managed `pending_product_photo_jobs` row, and navigates immediately. Rust processes persisted jobs in the background, creates/reuses the local asset, updates `products.image_asset_id`, records sync outbox changes, deletes temp inputs, and retries unfinished jobs on app startup or sync cycles.

**Tech Stack:** SolidJS, Tauri commands, Rust async tasks, SQLx SQLite, Drizzle sqlite-proxy, Vitest, Cargo tests, Ultracite.

---

## Behavioral Contract

1. Picking from camera/gallery still only stages a temp image and preview.
2. Submitting the product form must not await compression.
3. Once a staged photo job is accepted by Rust, Rust owns the temp file.
4. Frontend must not delete an accepted temp file on form unmount.
5. Product list should show a pending preview if `image_asset_id` is not ready yet.
6. If the app process dies after submit, pending jobs must remain in SQLite and resume on next app start or sync trigger.
7. If compression succeeds, Rust must update the product FK and queue product/assets sync.
8. If compression fails because the temp file disappeared, product save remains valid and the job is marked failed with a clear `last_error`.

```ts
interface PendingProductPhotoPreview {

export async function getPendingProductPhotoPreviewUrl(
  productId: string | null | undefined
): Promise<string | null> {
  if (!productId) {
    return null;

  const preview = await invoke<PendingProductPhotoPreview | null>(
    "get_pending_product_photo_preview",
    { productId }
  );
  if (!preview?.previewBase64) {

  return `data:${preview.previewMimeType};base64,${preview.previewBase64}`;
}
```

Add:

```rust

pub async fn process_pending_product_photo_jobs(
    app: AppHandle,
    state: State<'_, AppState>,
    limit: Option<i64>,
```

This delegates to:

```rust
async fn process_pending_product_photo_jobs_inner(
    app: &AppHandle,
    pool: &SqlitePool,
    limit: i64,
) -> Result<i64, String>
```

Processing algorithm:

1. Select jobs with `status IN ('pending', 'failed')`, ordered by `created_at`, limited by input.
2. For each job:
   - Mark `processing`, increment `attempts`, clear `last_error`.
   - Read temp path.
   - Run image compression through existing `process_image_bytes` in `spawn_blocking`.
   - Call `prepare_local_product_image_asset_inner`.
   - Update `products`:
     ```sql
     UPDATE products
     SET image_asset_id = ?1,
         is_synced = 0,
         updated_at = ?2
     WHERE id = ?3
       AND merchant_id = ?4
       AND deleted_at IS NULL
     ```
   - Insert/update sync outbox for product update.
   - Mark job `done`.
   - Delete temp input if safe.
3. On per-job error:
   - Mark job `failed`.
   - Store `last_error`.
   - If file missing or path invalid, do not retry forever.
4. Return number of successfully processed jobs.

Logs:

```text
[PHOTO-DEBUG] product_photo_jobs:start limit=...
[PHOTO-DEBUG] product_photo_job:start job_id=... product_id=...
[PHOTO-DEBUG] product_photo_job:asset_prepared job_id=... asset_id=...
[PHOTO-DEBUG] product_photo_job:product_linked job_id=... product_id=... asset_id=...
[PHOTO-DEBUG] product_photo_job:done job_id=...
[PHOTO-DEBUG] product_photo_job:failed job_id=... error=...
[PHOTO-DEBUG] product_photo_jobs:done processed=...
```

## Risk Notes

1. This adds a local-only migration. It must not be added to API sync table lists.
2. The preview base64 should be temporary and removed when job reaches `done`; otherwise it can bloat SQLite.
3. If the product is deleted before the job finishes, mark the job done/failed and delete the temp file without linking the asset.
4. If a second photo is picked for the same product before the first job finishes, the newest job should win. Older safe temp files should be deleted best-effort.
5. Rust code changes require `cd apps/pos-app && ./scripts/dev`; app reopen alone is not enough.

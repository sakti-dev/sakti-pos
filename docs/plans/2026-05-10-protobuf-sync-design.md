# Protobuf Sync Transport Design

**Goal:** Move the POS sync transport from JSON HTTP payloads to protobuf for smaller request and response envelopes across all sync endpoints.

**Decision:** Use a new `packages/protobuf` workspace package as the single schema source. The TypeScript API consumes `ts-proto` generated code from `@repo/protobuf/sync`. The Tauri Rust client generates `prost` structs from the same `.proto` file in `apps/pos-app/src-tauri/build.rs`.

## Scope

Convert these sync endpoints to protobuf:

- `POST /api/sync/push`
- `POST /api/sync/status`
- `POST /api/sync/pull-events`
- `POST /api/sync/pull`

The current `GET` status, pull-events, and pull endpoints should become `POST` endpoints because protobuf requests need a binary body. Auth remains unchanged and continues to use the existing session token/cookie flow.

## Protocol

Create `packages/protobuf/proto/sync.proto` with request and response messages for push, status, pull-events, and full pull. The initial row transport uses protobuf envelopes with JSON row payload strings:

- `payload_json` for push tables
- `rows_json` per pulled table

This is a deliberate incremental step. It removes JSON request/response envelopes now while avoiding a risky full schema definition for every table row. A later protocol version can replace table row JSON strings with typed protobuf row messages table by table.

The server must keep deriving `merchantId` from the authenticated `outletId`. The client must not send `merchantId` as trusted sync scope.

## API Architecture

`apps/api/src/sync/routes.ts` should use a small local Elysia plugin in `apps/api/src/plugins/ts-proto.ts`. The plugin owns generic protobuf transport concerns:

- Parse `application/x-protobuf` bodies as `ArrayBuffer`.
- Decode request bodies with a route-level `proto.req` schema generated by `ts-proto`.
- Encode route handler return values with a route-level `proto.res` schema.
- Set `Content-Type: application/x-protobuf` on protobuf success responses.

Sync-specific payload conversion still belongs in `apps/api/src/sync/protobuf.ts`. That module should only map service objects to generated protobuf message shapes, for example converting pulled table arrays into `SyncTableRows` with `rows_json`.

The route handlers stay responsible for authentication, outlet access verification, outlet lookup, and calling existing service functions.

The plugin should not promise perfect route-body inference from runtime schemas. Handlers can use explicit generated request types at the boundary, for example `const request = body as SyncPushRequest`, while still avoiding repeated `Uint8Array` decode and response encode code.

The service layer in `apps/api/src/sync/service.ts` should remain JSON-object based. This keeps the business logic, topological push order, conflict handling, empty-string normalization, and event log behavior isolated from transport concerns.

## Client Architecture

The Solid status client in `apps/pos-app/src/lib/sync/api.ts` should encode a protobuf `SyncStatusRequest` and decode `SyncStatusResponse`.

The Rust sync implementation in `apps/pos-app/src-tauri/src/sync.rs` should encode and decode protobuf for push, pull, and pull-events. Keep the existing SQLite and `serde_json::Value` logic intact by adding small mapping helpers that convert protobuf table payloads to the current table-to-rows shape.

## Error Handling

Malformed protobuf should return HTTP 400 with a text or JSON error. Malformed embedded JSON should also return HTTP 400. Auth failures remain 401. Outlet access failures remain 403. Unknown outlets remain 404. Server sync failures remain 500.

For protobuf success responses, set `Content-Type: application/x-protobuf`. For protobuf requests, send `Content-Type: application/x-protobuf` and `Accept: application/x-protobuf`.

## Testing Strategy

Use TDD for the migration:

- Add schema generation tests before adding generated imports.
- Add plugin tests that prove protobuf request decode and response encode works with generated `ts-proto` classes.
- Add API route tests that send protobuf bytes and decode protobuf responses.
- Add helper tests for mapping JSON service payloads to protobuf table payloads.
- Add Solid status client tests for binary request and response behavior.
- Add Rust unit tests for protobuf request construction and response/table decoding helpers.
- Run existing sync service tests unchanged to prove business logic was not coupled to protobuf.

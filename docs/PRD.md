# Sakti POS — Product Requirements Document

## Overview

**Sakti POS** is an offline-first point-of-sale application for Indonesian food & beverage businesses (cafes, quick-serve restaurants, warung). Built as an Android app using Tauri 2.0 with SolidJS frontend and Rust backend.

## Problem Statement

Small F&B businesses in Indonesia need a simple, affordable POS system that works without internet connectivity. Existing solutions are either cloud-dependent (unusable offline), too expensive, or overly complex for counter-service operations.

## Target Users

| Role | Description |
|------|-------------|
| **Owner** | Full access: menu management, user management, reports, settings |
| **Manager** | Menu management, order history, daily reports |
| **Cashier** | Take orders, process payments, view order history |

## Platform

- **Primary:** Android tablets and phones (Tauri 2.0 mobile target)
- **Architecture:** Offline-first with local database, cloud sync deferred to v2

## V1 Scope

### In Scope

1. PIN-based authentication with role-based access control
2. Menu management (categories + products CRUD)
3. Ordering flow (browse menu → cart → checkout)
4. Payment recording (cash + QRIS)
5. Order history with line-item details
6. User management (owner/manager only)

### Deferred to V2+

- ESC/POS thermal printer integration
- Advanced reporting and analytics (sales by product, category, payment method, hourly breakdown, trends, comparison periods, export)
- Cloud sync / multi-device
- Product variants and modifiers
- Inventory / recipe costing
- Image upload for products
- Split payments
- Table service

### Architecture: Drizzle sqlite-proxy pattern

```
SolidJS (Drizzle ORM)
    │
    │  type-safe queries serialized as SQL + params
    ▼
Tauri Command Bridge (IPC)
    │
    │  Rust Tauri commands: db_query, db_execute, db_execute_batch
    ▼
Rust (libsql)
    │
    │  executes against local SQLite file
    ▼
sakti-pos.db (app data directory)
```

The frontend defines Drizzle schema in TypeScript. Queries are serialized by the `sqlite-proxy` driver and sent over the Tauri IPC bridge as raw SQL with parameterized values. The Rust backend executes them via libsql and returns results as JSON. Migrations are generated by Drizzle Kit and embedded in the Rust binary, executed on app startup.

|--------|------|-------------|-------------|

| quantity | INTEGER | NOT NULL | Quantity ordered |

| subtotal | INTEGER | NOT NULL | quantity × unit_price |
| created_at | TEXT | | ISO 8601 datetime |

### Design decisions

- **Monetary values in whole IDR** — Indonesian Rupiah has no fractional units in practice
- **Product name and price snapshots on order_items** — menu changes must not affect historical order records
- **Daily sequential order numbers** — format `YYYY-MM-DD-NNN` for easy human reference and daily reconciliation
- **Soft deletes** (`is_active` flag) — preserves data integrity for historical orders
- **ISO 8601 text dates** — simpler than Unix timestamps for debugging and queries

## User Flows

### Authentication

1. App shows PIN pad with user list (names shown, not PINs)
2. User taps their name, enters 4-6 digit PIN
3. System validates PIN hash against `users` table
4. On success: store user session in memory (SolidJS reactive store), navigate to appropriate screen based on role
5. On failure: shake animation, retry

### Ordering (Cashier)

1. POS screen loads with category tabs on top, product grid below
2. Tap category tab → shows products in that category as large buttons (name + price)
3. Tap product → adds to cart (right panel). If already in cart, increments quantity
4. Cart shows item list with +/- quantity controls and running total
5. Tap "Bayar" (Pay) button → payment dialog opens
6. Select payment method: Tunai (Cash) or QRIS
   - **Cash:** Enter amount received, system calculates change (kembalian)
   - **QRIS:** Show confirmation, mark as paid
7. Confirm payment → order saved to DB with status `completed`, cart clears
8. Order number displayed on screen (e.g., "2026-04-30-001")

### Menu Management (Manager/Owner)

1. Navigate to Menu Management page
2. **Categories tab:** List of categories with add/edit/toggle active
3. **Products tab:** Filterable by category, list with add/edit/toggle active
4. Add/edit product: name, category (dropdown), price (numeric input), optional image URL, sort order

### Order History

1. Chronological list of orders (newest first)
2. Filter by date range
3. Tap order → expand to see line items, payment details, cashier name
4. Daily summary totals at top (total orders, total revenue, by payment method)

### User Management (Owner)

1. List of users with name, role, active status
2. Add user: name, PIN, role
3. Edit user: change name, role, reset PIN, toggle active
4. Cannot deactivate or change role of the last owner

## Rust Backend (Tauri Commands)

### Database commands

```
db_query(sql: String, params: Vec<Value>) → Vec<HashMap<String, Value>>
db_execute(sql: String, params: Vec<Value>) → ExecuteResult { last_insert_id, rows_affected }
db_execute_batch(statements: Vec<Statement>) → void
db_run_migrations() → void
```

### Database initialization

- DB file: `{app_data_dir}/sakti-pos.db`
- Created automatically on first launch
- Migrations embedded in Rust binary, run on app start (idempotent via migration tracking table)
- Seed data: one default owner account (PIN: 1234, must be changed on first login)

## UI/UX Guidelines

- **Touch-first:** All interactive elements minimum 48px tap target
- **Large product buttons:** Easy to tap on Android tablets
- **Cart always visible:** Split-screen layout on tablets (products left, cart right)
- **Indonesian language UI:** All labels in Bahasa Indonesia
- **Fast workflow:** Minimize taps from product selection to payment completion
- **Offline indicator:** Show persistent status bar when offline (informational only, app works fully offline)

## Non-Functional Requirements

- **Startup time:** < 2 seconds to login screen
- **Order processing:** < 500ms from "Pay" tap to order saved confirmation
- **Data integrity:** Orders are never lost; all writes use transactions
- **Storage:** SQLite database should handle 100K+ orders without performance degradation
- **Security:** PINs stored as hashes (argon2 or bcrypt), not plaintext
